# Dealbreak content implementation audit — Artifacts and Enhancements

**Read-only audit, September 24, 2026.** Source of intended content: `the old game-data workbook (removed 2026-10-25)`, sheets **Artifacts** and **Enhancements**, header row 1 and populated rows 2–101. Source of implementation: current working-tree code, the live `Assets/Scenes/Game.unity/GameController` catalog bindings, and authored assets under `Assets/Data/Relics/` and `Assets/Data/Enhancements/`. `DEALBREAK_DEVELOPMENT.md` and `Locus/knowledge/plan/dealbreak-remaining-roadmap-implementation.md` supply context, not proof of an effect. No gameplay, asset, scene, test, or workbook changes were made. **Do not interpret this audit as authorization to add or rebalance content.**

## Scope, classification, and identity caveat

Each sheet has **100 unique ID-bearing rows**. Artifacts: **35 defined effects** (`rel_001`–`rel_034`, `rel_100`) and **65 ID-only placeholders** (`rel_035`–`rel_099`). Enhancements: **11 defined effects** (`enh_001`–`enh_011`) and **89 ID-only placeholders** (`enh_012`–`enh_100`). All **200** IDs are accounted for below. The placeholders have no name, tier, effect, or other rule; they are **Not Implemented / unspecified**, rather than 154 invented designs. There are no workbook rows with content but no ID.

Classification is **effect-and-entry oriented**, not a claim that workbook IDs are live. **Implemented** = a playable authored asset matches the stated effect/trigger substantially (even if the workbook ID is not used); **Partially Implemented** = a playable close analogue or a material subset exists; **Needs Rework** = a same-name/suit analogue exists but implements a *different* intended rule; **Not Implemented** = no rule is actually specified for an ID-only row; **Requires New Architecture / Rule Support** = a defined effect is absent and cannot be delivered faithfully by merely authoring current fields. This last category includes narrowly scoped missing rule hooks as well as major systems; the dependency/risk column separates them. **Needs Rework is a spreadsheet-to-prototype mismatch, not a mandate to replace approved live mechanics.** The workbook's Status and Rarity columns are design metadata, not runtime evidence.

**Important crosswalk:** none of the live assets uses a workbook `rel_###`/`enh_###` ID. Eight live Artifacts have IDs `club_power`, `heart_power`, `diamond_power`, `spade_power`, `artisan_tools`, `reinforced_sleeves`, `victory_draught`, `golden_compass`; four live Enhancements have IDs `sharpened`, `reinforced`, `mending`, `quickdraw`. All 12 are assigned to `Assets/Scenes/Game.unity/GameController`; the other workbook entries are not in the active catalogs. `Assets/Editor/GameDataGenerator.cs` hardcodes these 12 assets; it does **not** ingest the workbook. No runtime rarity, tier, `Upgrade From`, or tier-replacement model exists. Therefore even an effect-level **Implemented** entry does not mean its literal workbook ID, tier chain, price, or distribution is implemented. Spreadsheet Price is blank for all defined rows audited here; the live assets have independent prototype prices.

**Code-path abbreviations used in every entry below:** **R** = `Assets/Scripts/Data/RelicData.cs` (`RelicData`); **E** = `Assets/Scripts/Data/CardEnhancementData.cs` (`CardEnhancementData`); **I** = `Assets/Scripts/Data/CardInstance.cs` (`CardInstance`); **C** = `Assets/Scripts/Managers/CombatManager.cs` (`CombatManager`); **K** = `Assets/Scripts/Managers/CardManager.cs` (`CardManager`); **Z** = `Assets/Scripts/Data/CardCollection.cs` (`CardCollection`); **D** = `Assets/Scripts/Combat/CombatResolver.cs` (`CombatResolver`); **Q** = `Assets/Scripts/Combat/CombatReactionQueue.cs` (`CombatReactionQueue`); **RM** = `Assets/Scripts/Managers/RunManager.cs` (`RunManager`); **M** = `Assets/Scripts/Data/RunMapGenerator.cs` (`RunMapGenerator`); **S** = `Assets/Scripts/Data/ShopOffer.cs` (`ShopOffer`). `Assets/Scripts/UI/EnhancementTargetUI.cs` is the shared Shop/Upgrade owned-card picker. Live asset paths are written out when there is an actual analogue. **Fit** in each row means whether the *current* R/E data shape can express the complete effect cleanly: **Yes**, **Extension** (a small typed hook/filter/field plus execution), or **No** (new action/turn/map/zone/state rule first). “No” does not imply a wholesale rewrite.

## Current Artifact system architecture

- `RelicData` is a shared immutable-in-play ScriptableObject definition with ID/display/price, suit and enhanced-card filters, integer attack multiplier/flat bonus/defense bonus, three per-card commitment hooks (reduce target ATK by base card value, recycle discarded cards by base value, draw by base value), and encounter-victory heal/bonus Gold. It has a capacity category (`Persistent` or `NonSlot`) but no tier/rarity, dynamic conditions, incoming-player-damage modifier, turn/map/defense/draw events, upgrade relationship, stacking policy, or per-artifact counters.
- `CardManager` owns run-local `ownedArtifacts` plus duplicate IDs, enforces **five** Persistent slots (NonSlot exempt; duplicates still rejected), purchases before adding, and resets on new run. `GameController` injects the eight scene-bound definitions. `RunManager` builds cached deterministic Shop offers, prices, and target-neutral Enhancement Upgrade offers; it has no Artifact tier-upgrade/replacement path. Adding an asset to `Assets/Data/Relics/` alone does **not** make it available in the Game scene.
- Actual attack in **C** multiplies matching integer multipliers, then adds matching flat bonuses to the enhanced card's attack; actual defense sums card and matching flat defense bonuses. `R.ModifyAttack/ModifyDefense` exist and are used in isolated tests, but **C does not call those methods**: changing their bodies alone would not change actual combat. Card-commit reactions run in deterministic source order via **Q**, then hits go through **D** (modifiers before one Shield charge per positive hit). Player `ModifyIncomingCombatDamage` currently returns its input unmodified (`Assets/Scripts/Data/PlayerRuntime.cs`). Unblocked multi-enemy attacks have separate defense requirements, then one aggregated player-damage hit. No authored multi-hit card is present, although C supports a staged hit count.

## Current Enhancement system architecture

- `CardEnhancementData` (**E**) contains a shared definition, one flat attack bonus, one flat defense bonus, and heal/draw **on play** amounts. **I** stores exactly one definition reference on a uniquely identified run-owned card; `TryApplyEnhancement` rejects a second and provides no replacement, removal, per-card mutable counter, or separately persisted absorbed damage. Base card definition and another same-rank card are unaffected. `CardCollection` (**Z**) owns deck/hand/discard/ownership and cannot remove a card from ownership through an authored effect. The default hand limit is `CardManager.HAND_SIZE = 8`.
- **C** computes attack/defense from **I**, enqueues heal/draw for the *played* card once at card commitment, and resolves damage per hit. Critical RNG currently rolls only for a valid **Ace pair**, once per paired action from the independent `combat-critical` stream supplied by **RM**; neither ordinary single-card criticals nor Enhancement-specific chances exist. `OnDamageResolved` reports hit results but is not an authored Enhancement trigger registry. Target choice and purchase revalidation belong to **RM**/**K** and `EnhancementTargetUI`; the four active assets have no tier/rarity fields.
- Current `Mending` is **heal 2 on play**, not a while-in-hand heal. Current `Reinforced` gives +3 defense and is a close gameplay analogue of workbook `Hardened`, not a workbook-ID match. These are deliberately different from the spreadsheet in their current playable form.

## Expansion assessment and minimal architecture recommendations

### Safe additions *without* refactoring

- The existing effect families can be authored and scene-cataloged safely with the **present rules**: suit-filtered integer per-card attack multipliers (`rel_001` effect), unconditional or enhanced-card-filtered flat attack/defense, after-victory flat heal/Gold, base-value ATK reduction/recycle/draw, and on-play per-card heal/draw or flat attack/defense Enhancements. `enh_001`/`enh_004` already exist by name and effect; `enh_002` has a `Reinforced` analogue. **There is no additional wholly new, fully specified defined workbook effect among the other rows that is a data-only addition**: condition, trigger, cap, hand capacity, or timing must change first. Do not omit Dagger's cap, Sword's threshold, or Tome's extra start draw to make them seem data-only.
- Authoring a supported family still requires a unique runtime ID, an asset, deliberate `GameController` catalog assignment, price/availability decision, and verification of five-slot capacity and deterministic offers. Keep workbook-ID mapping explicit; do not rename current IDs or re-run the hardcoded generator over user-authored assets as a shortcut.

### Brittle special cases to avoid

- Naming or ID switches inside **C/RM/K** for Heart/Spade/Diamond variants or tier upgrades; “fixing” `R.ModifyAttack` without integrating it into **C**; overloading `damageMultiplier` for action-total, fractional, thresholded, capped, or *incoming* damage; silent `Rank`/`Suit` mutation of shared `CardData` for Shifting.
- Reusing the global Ace-pair crit chance/stream for Lethal or Ace Emblem without an explicit composition and RNG-consumption policy; subscribing free-floating MonoBehaviours to hit/turn/draw events with unspecified order; letting Retaliation bypass the existing deterministic action/reaction and target checks.
- Treating a draw into a full hand as successful and immediately playing a non-owned/non-zoned card, destroying a defense card by deleting a UI view, or storing Devouring's accumulated bonus on shared `CardEnhancementData`. A second Enhancement slot or replacement must not be silently introduced to honor Devouring's note.
- Offering tier-1 and tier-2 same-name assets as unrelated purchases without explicit replacement, duplicate-ID, five-slot and cached-price rules; implementing extra turns as ad hoc state toggles that re-enter retaliation or recurse infinitely; inventing spreadsheet-omitted Gold, AoE damage, diminishing-returns formulas or Glass self-damage semantics.

### Smallest *recommended* foundations before risky content (proposals, not changes)

1. **Decide the rules and crosswalk first:** choose which spreadsheet effects supersede or coexist with approved prototype powers; record literal workbook ID ↔ live ID, tier/rarity/upgrade parent, price, slot occupancy and ownership/upgrade policy. Resolve ambiguous `rel_003`, `rel_026`, `rel_030`, `rel_031`/`rel_032`, `enh_003`, `enh_009`, `enh_010` before coding. Avoid speculative tier/rarity distribution until approved.
2. **Add small typed effect contexts at real boundaries, not name switches:** reuse **Q** for deterministic action/hit/reaction order, then explicitly expose only needed encounter start, card commit, resolved hit, matched defense, turn transition, draw attempt, map-node completion and hand-zone enter/leave hooks. Carry stable card/enemy identity, action ID, target, source, and once-per-action versus once-per-hit scope. Keep existing attack multiplier-before-flat semantics and Shield-after-positive-damage rule unless separately approved.
3. **Centralize conditional modifiers where applied:** extend actual **C/D** outgoing and player-incoming pipelines with typed filters (suit, enhanced, HP threshold, attack threshold), stage-aware caps/fractional rounding and preview consistency. A player-damage modifier should respect damage origin (combat vs event HP cost), aggregate retaliation and Shield ordering. Do not create a general-purpose effect interpreter merely for the first numeric item.
4. **Only as demanded by a batch:** add a run-local `CardInstance` progression component for Devouring; a single derived hand-cap authority for Arsenal/Overflow; explicit turn-grant state for Cheater/Dwarf; stable tier replacement rules; and a distinct effective-suit/action-combination model for Shifting, Hands and Royal. Route/map effects need a named independent seeded stream and defined reveal/target policies. Tests should characterize current semantics before any such additions.
